# Cycle Master 剧情原子内容块与对话分镜修复计划

> **文档版本**：v1.0
> **制定日期**：2026-07-20
> **关联计划**：`11_Phase1-5残留问题修复计划.md`
> **当前状态**：R0～R5 已完成；v2 已单源化，待用户视觉体验验收
> **决策结论**：采用“剧情 JSON 格式与内容 + 后端契约 + 前端播放器”三层协同修改，不采用只改前后端的补丁方案。

---

## 一、问题与修复目标

当前 v1 剧情把“台词、动作、叙述”混写在同一个字符串中；现有 v2 迁移又把部分完整段落整体标成了 `dialogue`。因此前端只能把整个段落放进气泡，出现以下错误：

```text
"你知道吗，荔湾广场那个地方——"她压低声音，"我查过了……"
```

这段内容实际包含三个需要分别点击、分别播放的语义单元：

1. 燕妍台词：“你知道吗，荔湾广场那个地方——”
2. 正文叙述：“她压低声音，”
3. 燕妍台词：“我查过了。1993 年施工的时候……”

本计划的目标是把全部剧情内容改为**有明确类型、明确说话人、明确顺序的原子内容块**，使前端不再分析引号或猜测文本性质，并修复选择结果与下一组选项错位、提前出现、跳过内容等问题。

---

## 二、方案比较与最终决策

| 方案 | 做法 | 优点 | 根本问题 | 结论 |
|---|---|---|---|---|
| A：只改前后端 | 保留混合字符串，在后端或前端用引号、正则和关键词即时拆分 | 初期改动较小 | 引号也可能表示书名、引用、回忆或心理活动；无法稳定判断说话人；错误会随剧情增加反复出现 | 不采用 |
| B：JSON + 后端 + 前端一起改 | JSON 明确记录每个原子块；后端校验并按顺序返回；前端逐块播放 | 语义稳定、可测试、便于编剧维护，能彻底解决截图问题 | 需要迁移并人工复核现有剧情 | **采用** |

### 2.1 采用方案 B 的原因

- “这句话是谁说的、是不是旁白、前后顺序是什么”属于剧情源数据，而不是 UI 推断逻辑。
- 运行时用正则拆引号无法可靠区分人物台词、引用资料、书名、内心独白和嵌套引语。
- 只改前后端会把内容错误隐藏在算法中，后续每新增一种写法都可能再次破坏播放。
- 当前 v2 已经具备 `ContentBlock[]` 的基础，主要缺陷是块粒度过粗和迁移策略不严谨，不需要推翻整个 v2 方向。

## 三、目标剧情格式

### 3.1 原子内容块示例

```json
[
  {
    "id": "C.choice.exchange_info.result.02.dialogue",
    "type": "dialogue",
    "speaker_id": "npc_yan_yan",
    "text": "你知道吗，荔湾广场那个地方——"
  },
  {
    "id": "C.choice.exchange_info.result.03.narration",
    "type": "narration",
    "text": "她压低声音，"
  },
  {
    "id": "C.choice.exchange_info.result.04.dialogue",
    "type": "dialogue",
    "speaker_id": "npc_yan_yan",
    "text": "我查过了。1993年施工的时候，挖出了八口棺材。八口。死囚的棺材。而且那不是普通的墓——棺材底下发现了一个老青砖砌的地下空间，里面画满了道教符文。"
  }
]
```

### 3.2 强制编写规则

1. `dialogue` 只保存人物实际说出口的文字，不保存外层引号，不夹带“她说”“他问”“压低声音”等动作或提示语。
2. `narration` 保存场景、动作、神态、心理和说话提示，不显示人物头像，不使用对话气泡。
3. `system` 只保存获得道具、属性变化、线索更新等系统提示；实际状态变化仍由结构化 `effects` 执行。
4. `dialogue.speaker_id` 必填；`player` 固定显示在右侧，所有 NPC 固定显示在左侧。
5. 数组顺序就是唯一播放顺序；一个内容块对应一次独立的打字机播放和一次继续操作。
6. 条件使用 `when` 字段，不把 `{{#if}}`、效果标记或控制语法写入文本。
7. 内容块 ID 必须稳定且唯一；只修改文字时不改 ID。

### 3.3 JSON 不承担的职责

- 不保存气泡宽度、坐标、动画时长等 UI 细节。
- 不保存“第几个块在左边”这类派生信息。
- 不要求编剧写 HTML、Markdown 控制标签或前端类名。

## 四、三层职责边界

### 4.1 剧情 JSON

- 明确每个内容块的 `type`、`speaker_id`、`text`、`when` 和顺序。
- 分别在 `entry_sequences[].blocks` 与 `choices[].result_blocks` 中组织入场内容和选择结果。
- 作为剧情内容与运行图的唯一事实源；已验收的 v2 不再依赖旧 v1 数据。

### 4.2 后端

- 加载并严格校验 v2 JSON。
- 根据游戏状态筛选 `when`，完成变量插值，并保持原数组顺序。
- API 原样返回结构化 `entry_blocks` 和 `result_blocks`，不在运行时猜测引号、不重排对话。
- 选择提交后返回完整结果块与下一节点信息，不让前端自行拼接旧字段。

### 4.3 前端

- 使用一个统一播放队列消费后端返回的内容块。
- `narration` 使用正文组件；`dialogue` 根据 `speaker_id` 使用左/右气泡；`system` 使用独立提示组件。
- 当前块未完成打字时，首次点击只补全当前块；再次点击才进入下一块。
- 只有当前队列全部播放完毕后，才允许刷新或显示下一组选项。
- 不使用引号正则、数组奇偶或文本关键词判断块类型及左右位置。

## 五、执行步骤

### R0：冻结基线与建立样例（不改变运行时）

- 记录当前 30 个节点、143 个选项、入场块和结果块数量。
- 把用户截图对应文本建立为首个“黄金样例”，明确预期序列为 `dialogue → narration → dialogue`。
- 保存当前严格校验、后端测试和前端构建结果，作为回归基线。
- 检查被中断的试验性拆分代码；在方案确认前不运行迁移、不覆盖 `data/story_data_v2`。

**完成条件**：基线报告可重复生成，且没有修改当前可运行数据。

### R1：完善 schema 与静态校验器

- 固化三类内容块和 `speaker_id` 约束。
- 增加以下错误或审计规则：
  - `dialogue` 缺失 `speaker_id`；
  - `dialogue` 保留成对外层引号；
  - `dialogue` 中疑似夹带“她说、他问、压低声音、合上、掏出、看着”等叙述；
  - `narration` 中存在明显直接引语候选；
  - 内容块 ID 重复或不稳定；
  - 条件模板或效果标记泄漏到文本。
- 疑似规则生成审计报告，不能把所有命中项直接自动改写。

**完成条件**：坏样例被拒绝或明确列入人工审计，合法样例通过严格校验。

### R2：非破坏性迁移与人工内容复核

- 迁移工具只输出到新的候选目录，不覆盖当前 v2，也不修改 v1。
- 自动拆分只作为候选生成手段，并且只在已经确定说话人的段落范围内工作。
- 按原文顺序生成 `dialogue`/`narration` 候选块；保留源文件和段落索引，便于对账。
- 全量人工复核所有含台词的入场内容和选择结果，重点检查：
  - 多段连续台词；
  - 台词中插入动作；
  - 文献引用、书名和转述；
  - 主角与 NPC 交替发言；
  - 嵌套引号、缺失引号和不规范标点。
- 输出迁移对账报告：源文本数、生成块数、自动拆分数、人工修正数、未确认数。

**完成条件**：30 个节点和 143 个选项全部对账，未确认项为 0，旧文本没有无故丢失。

### R3：后端契约收口

- 后端仅执行 schema 校验、条件过滤、变量插值和顺序透传。
- 统一同节点与跨节点选择的响应格式。
- 确保同节点流程为“结果块全部播放 → 刷新选项”；跨节点流程为“结果块全部播放 → 转场 → 新节点入场块 → 新选项”。
- 为入口块、选择结果块、条件块和存档恢复增加单元/API 测试。

**完成条件**：API 对黄金样例返回严格的三个原子块，顺序、类型和说话人完全正确。

### R4：前端播放器与 UI 收口

- 以单一有限状态机管理：`idle → typing → awaiting_continue → transitioning → choices`。
- 只保留一个播放队列、一个当前块和一个打字机任务；切换节点或读档时取消旧任务。
- 对话区域采用 NPC 左、主角右的气泡布局；正文独立显示，不伪装成气泡。
- 同一角色连续台词可以连续出现在同一侧，但每个原子块仍独立播放。
- 选择提交时锁定整组选项，避免重复请求；旧响应使用 turn/request ID 丢弃。
- 保持岭南民俗、中式恐怖、低饱和的视觉方向，但不复制其他游戏素材或布局。

**完成条件**：截图样例按三次播放正确呈现，且选择不会提前出现、闪回或错位。

### R5：全量回归与替换

- 执行 v2 严格校验、图可达性、后端单元/API、前端类型检查和生产构建。
- 覆盖同节点选择、跨节点选择、连续对话、主角发言、条件内容、快速点击、读档恢复。
- 在 1280×720、1366×768、1920×1080 和窄屏视口检查布局。
- 浏览器自动化不可用时必须明确记录，不能以构建成功替代视觉验收。
- 候选数据全部通过后再切换运行时目录；保留可回滚的旧 v2 数据。

**完成条件**：所有自动化检查通过，关键剧情人工抽验通过，运行时正式使用复核后的原子块数据。

## 六、重点测试与验收标准

### 6.1 截图问题的精确验收

该段 API 与 UI 必须严格按以下顺序返回和展示：

```text
1. dialogue / npc_yan_yan / 你知道吗，荔湾广场那个地方——
2. narration / 她压低声音，
3. dialogue / npc_yan_yan / 我查过了。1993年施工的时候……
```

- 第 1、3 块显示为左侧燕妍气泡。
- 第 2 块显示为独立正文。
- 每块分别使用打字机效果。
- 当前块未结束时不显示下一块或选项。
- 全部结果块结束后才显示接下来的选项。

### 6.2 数据完整性

- 30 个现有节点全部通过 schema 与图校验。
- 143 个现有选项全部完成源文本对账。
- 所有可游玩节点保持可达，不因文本迁移改变条件、效果和路由。
- `dialogue` 中没有外层引号和混入的叙述动作。
- 不存在未解析模板、效果标记或空内容块。

### 6.3 播放状态

- 同节点：选择 → 结果块 → 新选项。
- 跨节点：选择 → 结果块 → 转场 → 入场块 → 新选项。
- 快速点击不会重复提交或跳过两块。
- 读档不会重放错误节点、丢失结果或提前展示选项。
- NPC 始终在左，主角始终在右，不受块索引影响。

## 七、风险控制与回滚

1. 迁移期 v1 剧情只作为文本对账依据；单源切换完成后从工作树移除。
2. 新迁移结果先写入候选目录；禁止迁移脚本直接覆盖人工修正后的正式 v2。
3. 自动引号拆分不是最终真相，所有疑似项必须经过审计或人工确认。
4. 切换正式数据前保留当前 v2 快照，并记录 schema/manifest 版本。
5. 后端与前端在迁移期间可短期兼容旧 v2，但正式验收后移除运行时猜测和双分支，防止长期维护两套逻辑。
6. 任何文本迁移都不得改变选择条件、effects、next、循环计数和存档语义；这些字段通过结构化对账锁定。
