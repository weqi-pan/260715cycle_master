## 二、原第一节问题逐项复核

### 2.1 K 跃迁选项缺少 `next_node_id`

**结论：不存在，原审查使用了过时代码。**

当前 [special_router.py](../backend/app/engine/special_router.py) 中：

- `__warp_K_enter` 明确返回 `next_node_id="K"`；
- `__warp_K_exit_{target}` 明确返回 `next_node_id=target_id`；
- `resolve()` 生成的入口与出口 `ChoiceData` 也具有相同目标。

因此不应再执行原文“补 3 行”的修复。`ChoiceResult.next_node_id` 默认空字符串仍属于契约可收紧项，但不是 K 当前失效的证据。

**正确处理：**

- 将 `ChoiceResult.next_node_id` 改为必填非空字符串；
- 为静态选项、K 入口和 K 出口分别增加响应契约测试；
- 不改变已经正确的 K 路由逻辑。

优先级：P2，契约加固，不阻断当前玩法。

### 2.2 `cycle_variants` 在循环次数达到两位数时排序错误

**结论：真实存在，但只影响 v1 兼容文本路径。**

[engine.py](../backend/app/engine/engine.py) 的 `_resolve_node_content()` 对范围变体使用 `sorted(variants.keys())`，最后一次匹配覆盖前一次匹配。字符串字典序会使 `cycle_10+`、`cycle_11+` 与 `cycle_9+` 的优先级错误。

正式 v2 入场内容通过 `entry_sequences.priority/when` 解析，不走这段逻辑；但兼容层仍在运行且有回归测试，因此应修复而非忽略。

**正确方案：**

1. 新增失败测试：同时提供 `cycle_3+`、`cycle_9+`、`cycle_10+`、`cycle_11+`，断言循环 11 选择阈值最大的 `cycle_11+`。
2. 解析合法的 `cycle_N+` 阈值，筛选 `N <= cycle_count` 的候选项，再使用数值最大的 N。
3. 精确项 `cycle_N` 继续高于范围项 `cycle_N+`。
4. 对非法键给出明确错误或忽略策略，禁止 `int()` 异常泄漏为无上下文 500。

优先级：P1，低风险逻辑缺陷。

### 2.3 “只有 H→A 才算完整循环”过于严格

**结论：原判断不成立，不能按原建议放宽。**

当前产品语义及回归测试明确规定：

- H→A：完整循环，`cycle_count + 1`；
- J→A：捷径半循环，`half_cycle_count + 1`，不增加完整循环；
- K→A：跃迁，不构成循环；
- A→A：节点内调查，不构成循环。

若改为“任何非 A 节点回 A 都算完整循环”，会直接破坏 J/K 的已确认语义。当前 v2 图中也没有需要被遗漏计算的 G→A 正常完整循环边。

**正确处理：**

- 保留当前语义，不修改计数条件；
- 中期可把 `FULL_CYCLE_ENTRY_SOURCES` 和 `HALF_CYCLE_ENTRY_EDGES` 改为数据中的显式路由事件，减少硬编码；
- 数据化前必须先固化 H→A、J→A、K→A、A→A 四类契约测试。

优先级：P2，架构改善，不是当前缺陷。

### 2.4 `process_choice(save_id)` 是死参数

**结论：死参数真实存在，但原文所称“多玩家状态互相污染”不成立。**

`save_id` 仅出现在签名和注释中，函数体未使用。可是引擎并没有保存全局可变 `GameState`；每次请求都使用请求体传入的状态，因此死参数本身不会让不同玩家共享内存状态。`persistent_nodes` 已随 `GameState` 保存和恢复。

**正确方案：**

- 删除 `process_choice()` 的 `save_id` 参数及过时注释；
- 不在纯引擎层加入数据库访问；
- API 的客户端状态信任问题单独按 3.8 处理，不能借 `save_id` 顺带耦合存档数据库。

优先级：P2，代码清理。

### 2.5 `canDiscard` 硬编码道具白名单

**结论：真实存在，原修复方向不完整。**

[GamePlay.vue](../frontend/src/views/GamePlay.vue) 使用 `DISC` 集合决定可丢弃性；`ItemBrief` 只有 `id/name/count`，当前也没有可供运行时查询的统一道具定义仓库。只给 TypeScript 增加 `discardable` 字段不会自动产生可信数据。

**正确方案：**

1. 建立唯一道具定义源，至少包含 `id`、`name`、`stackable`、`discardable`、`cross_surface`。
2. 后端生成背包与遗留道具时从定义源补齐元数据，客户端不得自行猜测。
3. `ItemBrief` 增加只读元数据；前端使用 `item.discardable`。
4. 丢弃操作必须由后端 API 校验，不能只在前端隐藏按钮后直接修改本地数组。
5. 增加“可丢弃成功、不可丢弃被拒绝、读档后属性一致”的 API 测试。

优先级：P1，当前存在客户端单方面修改状态的风险。

### 2.6 跨面道具列表前端硬编码

**结论：真实存在，但仅是展示层重复；后端跨面逻辑已读取道具实例的 `cross_surface`。**

[StatusBar.vue](../frontend/src/components/player/StatusBar.vue) 维护 `CROSS` 集合；后端 `PersistentFound.cross_surface_items` 则根据道具实例的 `cross_surface` 字段计算。两者可能漂移。

**正确方案：**

- 与 2.5 共用统一道具定义源，不再创建第二套机制；
- 后端返回带 `cross_surface` 的 `ItemBrief`；
- 状态栏直接读取字段或使用后端返回的跨面集合；
- 增加新增跨面道具无需修改前端源码的测试。

优先级：P2，与 2.5 合并实施。

### 2.7 Speaker 名称映射重复

**结论：部分真实，原证据错误。**

前端确实在 `SPEAKER_NAMES` 中硬编码 NPC 显示名。但原文引用的后端 `FLAG_NAMES` 等映射并不是 NPC 名称映射，不能证明前后端重复。v2 的 `npcs_present` 当前只保存 ID，且多个含对话的子节点仍将其留空，无法直接作为名称事实源。

**正确方案：**

1. 建立 NPC 定义源：`id`、`display_name`、可选头像与样式信息。
2. `ContentBlock` 响应携带后端解析后的 `speaker_name`，或 Frame 携带本帧 speaker 字典。
3. 前端保留 `player → 我` 的本地化规则，其余名称不得从 ID 字符串猜测。
4. 数据校验器拒绝未知 `speaker_id`。

优先级：P2，数据一致性改进。

### 2.8 SQLite `story_nodes/choices` 是死代码

**结论：部分真实，当前不能直接删除。**

播放器已经只从 v2 JSON 加载剧情；但编辑器路由仍完整读写 SQLite 的 `StoryNode/Choice`，前端编辑器也调用这些接口。因此这些表对“游戏运行”是遗留路径，对“现有编辑器”仍是活代码。

**正确方案：**

1. 先决定编辑器目标：直接安全编辑 v2 JSON，或明确废弃编辑器。
2. 若保留编辑器，先实现 v2 文件的读取、Schema 校验、原子写入、引用校验和失败回滚。
3. 将编辑器切换到 v2 后，再删除 SQLite 故事 ORM、旧 `GraphLoader.load_all()` 与旧导入脚本。
4. `GraphBundle.from_story_v2()` 是当前运行时必要的适配器，不能随旧 `GraphLoader` 一起删除。
5. 删除前增加全仓引用检查和编辑器 CRUD 集成测试。

优先级：P1，双数据源会造成编辑结果不进入游戏。

## 三、确认新增及仍需修复的问题

### 3.1 不可选与已选选项仍显示给玩家

**结论：真实存在，按最新产品要求列为 P0。**

最新规则：

- 条件不满足的选项不显示；
- 已执行且当前重复策略不允许再次执行的选项不显示；
- 前端不展示灰色锁定项、锁定原因、删除线已选项；
- 后端仍必须拒绝伪造的不可用或不可重复请求。

当前实现与规则冲突：

1. `GameEngine.resolve_choices()` 会把 `locked_visibility="show"` 的失败条件选项作为 `available=false` 返回。
2. `GamePlay.vue` 遍历所有 `store.choices`，对不可用项只做禁用和置灰。
3. `chosenIds` 只存在于当前前端组件内，选过后仍保留按钮并显示删除线/勾号。
4. `repeat_policy` 已在 v2 Schema 和 143 个选项中存在，但未进入 `ChoiceData`、`GameState` 或引擎判定。
5. 刷新、读档或直接调用 API 会丢失前端 `chosenIds`，所以不能由前端承担权威判定。

#### 正确语义

| `repeat_policy` | 选过后的隐藏范围 |
|---|---|
| `always` | 不隐藏，可重复执行 |
| `once_per_visit` | 本次进入该节点期间隐藏；离开后再次进入可恢复 |
| `once_per_cycle` | 当前完整循环内隐藏；下一完整循环恢复 |
| `once_ever` | 永久隐藏，且必须随存档恢复 |

补充约束：

- 同节点 `stay` 不视为重新进入节点，不能重置 `once_per_visit`。
- travel/shortcut/warp 离开后再返回，才创建新的 visit。
- 条件失败与重复策略失败都由后端过滤，不返回给正常 Frame。
- `locked_visibility` 与最新产品规则冲突，应迁移为统一隐藏并从正式 Schema 删除；迁移期可读取但一律按隐藏处理。
- `process_choice()` 必须重新校验条件和重复策略，防止客户端提交隐藏选项 ID。

#### 状态与契约方案

在 `GameState` 中增加可序列化选择记录，而不是继续扩大前端 `chosenIds`：

- `node_visit_id`：每次真正进入节点时递增或生成稳定 ID；同节点 stay 保持不变。
- `choice_history`：按 choice ID 保存至少 `count`、`last_cycle`、`last_visit_id`。
- 新游戏初始化为空；选择成功后由后端原子记录；存档加载完整恢复。
- `ChoiceData` 保留 `repeat_policy`，从 v2 Loader 一直传递到引擎。

字段命名可在实现时依据 Pydantic 约定微调，但必须同时更新 Python Schema、TypeScript 类型、存档往返和 API 测试，禁止只改前端。

#### TDD 实施任务

**任务 A：固化可见性规则**

- 测试文件：`backend/tests/test_choice_visibility.py`
- 增加条件失败选项不出现在 `available_choices` 的失败测试。
- 增加伪造提交条件失败选项返回 4xx 的 API 测试。
- 修改 `resolve_choices()`：所有条件失败选项统一过滤。
- 删除前端 locked reason/样式分支前，先确保响应中不再出现不可用静态选项。

### 3.2 v1 `cycle_N+` 数值优先级错误

对应 2.2，确认进入近期修复批次。测试应先覆盖两位数阈值，再修改兼容解析器。

### 3.3 编辑器与 v2 唯一事实源分叉

对应 2.8，确认存在。编辑器当前修改 SQLite 不会改变播放器加载的 v2 JSON，属于功能正确性问题，而不仅是清理技术债。

### 3.4 道具丢弃由前端直接修改状态

除硬编码白名单外，[GamePlay.vue](../frontend/src/views/GamePlay.vue) 当前 `discardItem()` 直接 splice 当前 Frame 的 inventory，没有服务端效果、规则校验或可靠存档语义。

正确方案是新增后端 inventory action，由服务端校验 `discardable`、修改状态并返回新 Frame；前端不得直接修改 Pinia 中的服务端状态对象。

### 3.5 播放器职责与测试覆盖不足

`GamePlay.vue` 仍同时管理播放队列、打字机、请求防重、转场、音频、场景效果、背包、地图和存档。当前只有 `playbackTimeline.ts` 两项单测，没有 GamePlay、Store 或有效 E2E 覆盖。

这是可维护性风险，但不应与 3.1 的行为修复绑成一次大重构。先完成后端权威可见性与针对性测试，再单独拆播放器。

### 3.6 NPC 与道具元数据缺少统一运行时定义

对应 2.5、2.6、2.7。建议在编辑器 v2 化之前先设计只读定义目录及 Schema，避免编辑器再次围绕旧 SQLite 模型扩展。

### 3.7 `ChoiceResult.next_node_id` 契约过宽

虽然 K 当前正确，但空字符串默认值会掩盖未来漏填错误。应改为必填非空字段，并对所有响应选项做目标节点存在性校验。

### 3.8 API 信任客户端完整 `GameState`

`/api/game/choose/{node_id}` 接收客户端提交的完整状态，尚未绑定服务端 turn/save，也没有可靠的并发版本校验。客户端可修改道具、flag 或属性后请求选择。

短期至少校验 `node_id == state.current_node_id`、目标选择属于当前节点且当前可执行；中期使用服务端 session/turn ID 保存权威状态，客户端只提交 `turn_id + choice_id`。该问题与 3.1 的防绕过测试应共享 API 测试基础设施。

## 六、明确不执行的原建议

- 不再“修复 K 缺少 next_node_id”，因为当前代码已经正确。
- 不把任意非 A→A 路径都算完整循环，因为会破坏 J/K 语义。

- 不直接删除 StoryNode/Choice ORM；编辑器尚依赖它们。
- 不把 NPC `FLAG_NAMES` 当作名称重复证据。
- 不用前端 `chosenIds` 代替持久化重复策略。
- 不仅靠 CSS、禁用按钮或 `v-if` 修复选项规则；后端必须是唯一裁决者。

## 七、本计划完成定义

只有同时满足以下条件，才能关闭本计划中的选项问题：

- 正常 Frame 不包含任何条件失败选项。
- 已选选项严格按 `repeat_policy` 隐藏和恢复。
- stay、travel、shortcut、warp、完整循环的 visit/cycle 边界有明确测试。
- 刷新、读档和旧存档升级不会让已隐藏选项错误重现。
- 伪造 choice ID、篡改状态和重复请求不能重复执行效果。
- 前端不再展示锁定项、锁定原因、已选删除线或已选勾号。
- 后端全量测试、v2 严格校验、前端单测、生产构建和关键 E2E 全部通过。
